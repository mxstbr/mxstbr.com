# Webhook conformance audit — September 23, 2026

Scope: the server side of MCP Events webhooks, including discovery and shared occurrence/cursor rules. Poll and push remain disabled. This is a conformance review of an experimental draft, not certification against a ratified standard.

## Corrections found by this audit

1. Missing, expired and already removed subscriptions now return `-32011 NotFound` with `data.kind: "subscription"`. The previous implementation incorrectly returned success.
2. Subscription capacity and verification-rate limits now return `-32013 ResourceExhausted` with a typed `data.limit`. Capacity remains atomic under concurrent creates, with an early check before verification.
3. All finite integer TTL suggestions negotiate through clamping. Negative and unusually large integer suggestions no longer fail static validation; malformed non-integer values still do.
4. Subscribe requests selecting a recognized unsupported mode return `-32014 Unsupported`. No polling or streaming delivery was restored.
5. Unauthenticated production Events requests retain HTTP 401 and include the draft's `-32012 Forbidden` JSON-RPC error.
6. `maxAgeMs` now applies to the entire initial replay even when timestamps are not in commit order. The initial time floor is retained across workers until that replay is exhausted, without filtering future occurrences by an old subscription setting.

## Optional features and implementation choices

Only the handshake verification path is offered; the draft permits any one of its verification mechanisms. No-expiry grants, asymmetric server signatures, failure-driven subscription suspension, and dynamic catalog changes are not offered. Their conditional requirements therefore do not apply to this implementation. Receiver requirements are documented for clients; the chores server cannot prove a receiver durably forwards an acknowledged message to an agent.

The draft describes retry bookkeeping as in-memory, TTL-scoped state. This server stores the derived in-flight positions, acknowledgements, pending payloads and verification grants in Redis for the finite subscription lifetime so serverless workers can share them and honor their grants. It does not persist the client's request cursor as a separate canonical cursor. Fresh subscriptions after lapse still use the cursor supplied by the client. This is a deliberate durability choice beyond the draft's in-memory examples.

## Confidence and limits

The applicable wire requirements were traced to code and targeted tests. Independent signature interoperability is checked with the official receiver library; Redis behavior and the real MCP HTTP route are checked separately. No known mismatch remains in those tested webhook paths after the corrections above.

This audit does not establish compatibility with every emerging Events client or an unmerged proposal. It does not perform a positive production delivery to the user's eventual public receiver: callback lifecycle tests use injected receivers and disposable data, and live checks exercise discovery, authentication and validation without creating subscriptions or sending private chore data. An end-to-end subscription with the actual receiver remains the final deployment-specific interoperability check.
